================================================================================
Cloudflare WAF 规则表达式（备选路线 B —— 把 ai-memory.net 挂到 Cloudflare 前面）
================================================================================
生成日期：2026-09-24
对应文档：docs/hardening-2026-09-24.md §3
对应源站：deploy/harden_caddy.py（Caddy 侧的那套规则）

⚠️ 动手之前先读这两段，否则这份文件会误导你。

【一】本站现在不在 Cloudflare 后面，而且"挂上去"本身是一个有代价的决定
    DNS 走阿里云万网，A 记录直接指向 GCP 35.227.140.175，Caddy 直接对外。
    整站之所以把所有 CDN 资源本地化（deploy/localize_assets.py），就是因为国内
    直连境外 CDN 会白屏（DEPLOY.md §8.2）。Cloudflare 免费版没有中国大陆节点，
    加了之后国内用户的 TLS 握手与回源都要绕到境外。
    → 先在测试子域上挂一周，用国内线路实测首字节时间，再决定要不要动主域。

【二】免费版的自定义规则不支持正则
    这是本文档第一版最大的错误。Cloudflare 官方的规则能力表写得很清楚：

        套餐      自定义规则数   正则（matches 运算符）
        Free      5             不支持   ← 本站属于这一档
        Pro       20            不支持
        Business  100           支持
        Enterprise 1000         支持

    所以任何"把 Caddy 的 path_regexp 抄过来直接粘"的做法在免费版都会当场报错。
    下面所有表达式都只用免费版可用的运算符：
        eq / ne / contains / in / starts_with() / ends_with() / lower()
    文末附 Business 及以上才可用的正则版（与 Caddy 那份等价）。

粘贴位置

================================================================================
规则 1 / 4    扫描路径与配置泄露
================================================================================
名称：  拦扫描路径与配置泄露
动作：  Block
说明：  与 deploy/harden_caddy.py 里的 @blocked 规则一一对应，是它的无正则翻译版。

❌ 不要写成 contains "/backup"
   本站后端真的有 /api/ops/backup-logs 与 /api/ops/backup-status 两个接口。
   contains 是"路径里任意位置出现"，写成 contains 会把管理后台的备份状态接口
   一起打挂；而 Caddy 那份正则用的是 ^/(...|backup|...) 行首锚定，不会误伤。
   所以下面凡是 Caddy 里 ^/ 锚定的 token，一律用 starts_with()，这才是忠实等价。

❌ 不要用 http.request.uri.path.extension 去拦点文件
   该字段的官方语义是"路径最后一段里最后一个点之后的字符串"，并明确规定：
   若最后一段以点开头且不含其他点，则返回空字符串。
   也就是说 /.env → ""、/.DS_Store → ""，用 extension 永远拦不住点文件。
   点文件必须走 starts_with / contains。

表达式：

starts_with(lower(http.request.uri.path), "/.git")
or starts_with(lower(http.request.uri.path), "/.env")
or starts_with(lower(http.request.uri.path), "/.data")
or starts_with(lower(http.request.uri.path), "/.ds_store")
or starts_with(lower(http.request.uri.path), "/.aws")
or starts_with(lower(http.request.uri.path), "/.ssh")
or starts_with(lower(http.request.uri.path), "/.svn")
or starts_with(lower(http.request.uri.path), "/.hg")
or starts_with(lower(http.request.uri.path), "/.vscode")
or starts_with(lower(http.request.uri.path), "/.idea")
or starts_with(lower(http.request.uri.path), "/_preview")
or starts_with(lower(http.request.uri.path), "/index.html.")
or starts_with(lower(http.request.uri.path), "/wp-")
or starts_with(lower(http.request.uri.path), "/xmlrpc.php")
or starts_with(lower(http.request.uri.path), "/phpinfo")
or starts_with(lower(http.request.uri.path), "/phpmyadmin")
or starts_with(lower(http.request.uri.path), "/pma")
or starts_with(lower(http.request.uri.path), "/adminer")
or starts_with(lower(http.request.uri.path), "/config.php")
or starts_with(lower(http.request.uri.path), "/docker-compose")
or starts_with(lower(http.request.uri.path), "/dockerfile")
or starts_with(lower(http.request.uri.path), "/server.py")
or starts_with(lower(http.request.uri.path), "/requirements.txt")
or starts_with(lower(http.request.uri.path), "/backup")
or starts_with(lower(http.request.uri.path), "/database")
or starts_with(lower(http.request.uri.path), "/node_modules")
or starts_with(lower(http.request.uri.path), "/vendor")
or lower(http.request.uri.path) contains "/.git"
or lower(http.request.uri.path) contains "/.env"
or lower(http.request.uri.path) contains "/.aws"
or lower(http.request.uri.path) contains "/.ssh"
or lower(http.request.uri.path) contains "/.svn"
or http.request.uri.path.extension in {"py" "pyc" "json" "orig" "md" "log" "bak" "save" "tmp" "sql" "db" "sh" "env" "ini" "conf" "prev" "old" "swp" "pem" "key" "crt" "p12" "pfx" "yml" "yaml" "toml" "sqlite"}

几点说明：
  · lower() 是必需的。Cloudflare 的字符串比较区分大小写，而真实世界里的攻击
    路径是大小写混着来的（/.DS_Store、/WP-ADMIN/、/Config.PHP）。Caddy 那份
    正则用了 (?i)，这里用 lower() 达到同样效果。extension 字段本身已经是小写，
    所以扩展名那一支不需要再套 lower()。
  · 最后那 5 条 contains "/.xxx" 是嵌套情况（例如 /docs/.env、/a/b/.git/config）。
    starts_with 只锚行首、覆盖不到，所以必须单独列。
    注意这里**没有**写 "/.env/"（带尾斜杠）——Caddy 那份正则的末尾是 (/|$)，
    意思是"斜杠或路径结尾"都算命中，写成带尾斜杠就只能挡住目录形式、
    挡不住 /docs/.env 这种文件形式。这个差异是本地回放测出来的，不是看出来的。
    代价是 contains 比 Caddy 略宽（还会顺带挡住 /.env.example、/.gitignore），
    但那些本来也该挡，可以接受。
  · 扩展名白名单刻意不含 css / js / ico / png / svg / woff2 / txt / xml / html ——
    站点自己的门面（robots.txt、sitemap.xml、llms.txt、.well-known/security.txt、
    favicon、legal.html）和 assets/ 下的真实资源全在这几类里，拦错了等于把
    自己的门也锁上。
  · 已核对后端全部路由：没有任何接口路径以被拦的扩展名结尾（/api/dash/export、
    /api/dash/smtp/test 等最后一段的 extension 是 ""/"test"/"export"，都不在集合里），
    所以这条规则不会打挂 API。

规则 2 / 4    已知扫描器与自动化工具的 User-Agent
================================================================================
名称：  拦扫描器 UA
动作：  Block
说明：  免费版没有正则，只能逐个 contains 列举。这是一份"宁可少列、不要列错"的清单。

表达式：

lower(http.user_agent) contains "sqlmap"
or lower(http.user_agent) contains "nikto"
or lower(http.user_agent) contains "nuclei"
or lower(http.user_agent) contains "wpscan"
or lower(http.user_agent) contains "hydra"
or lower(http.user_agent) contains "metasploit"
or lower(http.user_agent) contains "masscan"
or lower(http.user_agent) contains "zgrab"
or lower(http.user_agent) contains "gobuster"
or lower(http.user_agent) contains "dirbuster"
or lower(http.user_agent) contains "wfuzz"
or lower(http.user_agent) contains "ffuf"
or lower(http.user_agent) contains "feroxbuster"
or lower(http.user_agent) contains "acunetix"
or lower(http.user_agent) contains "netsparker"
or lower(http.user_agent) contains "nessus"
or lower(http.user_agent) contains "openvas"
or lower(http.user_agent) contains "w3af"
or lower(http.user_agent) contains "skipfish"
or lower(http.user_agent) contains "nmap scripting engine"

刻意没有列进去的（列了会误伤自己）：
  · "curl" / "wget" —— 你自己的存活探活、以及别人的正常命令行调试都在用。
    本文件的验收命令就是 curl。把 curl 拦掉，出事时你连诊断都做不了。
  · "python-requests" / "go-http-client" —— 大量正常 SDK 与集成都用它。
  · 空的 User-Agent —— 见规则 4，默认不开。

另注：Cloudflare 免费版自带 Bot Fight Mode（安全性 → 机器人），
它是基于行为/指纹而不是 UA 字符串，比这张表管用得多，建议单独开。
但开了之后要观察 Security Events，确认没把搜索引擎误伤。


================================================================================
规则 3 / 4    方法白名单（静态资源只接受 GET / HEAD / OPTIONS）
================================================================================
名称：  静态站点方法白名单
动作：  Block
说明：  对应 harden_caddy.py 里的 @badmethod。差异要说清楚：
        Caddy 那份是挂在"静态 catch-all 的 handle 块"里的，天然只作用于静态文件；
        Cloudflare 在 zone 层面看不到 handle 块，只能用路径来近似。
        所以这里显式排除 /api/ 与 /auth/，其余一律只放行读方法。

表达式：

not starts_with(http.request.uri.path, "/api/")
and not starts_with(http.request.uri.path, "/auth/")
and not http.request.method in {"GET" "HEAD" "OPTIONS"}

说明：
  · /api/ 里全是 POST（登录、注册、控制台动作、头像上传、联系表单），必须排除。
  · /auth/ 是 GitHub OAuth 跳转，虽然只有 GET，排除了也不亏。
  · OPTIONS 留着是为了 CORS 预检，HEAD 是搜索引擎探活要用的。
  · 这条规则里的 "/api/" 与 "/auth/" **故意不加 lower()**，是刻意的：
    Cloudflare 的路径比较区分大小写，所以 POST /API/leads 不满足排除条件，
    会被这条规则拦掉（403）。后端路由本身也是大小写敏感的，/API/leads 到了
    应用层同样只会 404，所以拦掉它没有任何损失，反而更严。
    若给这两条加了 lower()，/API/ 就会被"排除"出去而放行到后端 —— 变松了。
  · 这条规则上线的当天就要回归一遍：登录、注册、控制台里点一圈、
    上传一次头像、提交一次联系表单。任何一处 405 都说明排除条件写漏了。


================================================================================
规则 4 / 4    空 User-Agent（可选，默认不要开）
================================================================================
名称：  空 UA 拦截
动作：  Block
说明：  真正的扫描器里有一批不送 UA。但空 UA 同样出现在非常正经的客户端里
        （老式监控脚本、部分内网探活、某些 IoT 设备）。开了之后必须先观察
        Security Events 再决定，否则最可能的结果是把自己的监控搞掉。

表达式（确认要开再用）：

http.host in {"ai-memory.net" "www.ai-memory.net"}
and http.user_agent eq ""
and not starts_with(http.request.uri.path, "/api/")
and not starts_with(http.request.uri.path, "/auth/")

免费版 5 条自定义规则的额度，以上用掉 3 条（开了第 4 条就是 4 条），
还剩 1～2 条机动，留给后续临时封禁某个 IP 段之类的一次性需求。

限流规则（免费版：1 条，计数窗口固定 10 秒，只能按 IP 计数）
================================================================================
位置：安全性(Security) → 安全规则 → 速率限制规则(Rate limiting rules)

名称：    登录/注册接口限流
表达式：
starts_with(http.request.uri.path, "/api/auth/")
or starts_with(http.request.uri.path, "/auth/")

参数：
  请求特征：IP 地址（免费版只有这一项，改不了）
  速率：    20 次 / 10 秒
  超过后：  阻止(Block)
  缓解时长：10 秒

⚠️ 为什么盯的是 /api/auth/ 而不是 /api/
    本站后端是单进程 Python（server.py），登录走 PBKDF2-SHA256 20 万轮，
    单次校验大约上百毫秒 CPU。也就是说**未登录的 /api/auth/* 是最便宜的
    CPU 打点**：一个攻击者不需要账号，只要并发几十个登录请求就能把这个
    单进程打到 100% CPU，正常用户全部超时。
    /api/ 下的其他接口都要先通过认证，攻击成本高得多，所以额度留给它们。

⚠️ 20/10s 这个数字是这么来的
    server.py 里已有的应用层限流 RATE_RULES['login'] = (12, 60)，即单 IP
    60 秒 12 次（约 0.2 次/秒）。边缘限流取 20/10s（2 次/秒）故意比应用层**宽**，
    这样正常用户永远先撞不到边缘规则，它只在有人开始打的时候才起来兜一层。
    边缘和应用层的职责不同：应用层负责精确业务限流，边缘负责挡住量。
    两边数字设反了（边缘比应用层还严）会让正常用户看到 Cloudflare 的 1020 页面，
    而不是应用自己的友好提示。

⚠️ 免费版限流挡不住分布式
    只按 IP 计数，且只有 10 秒窗口。撞库如果来自上千个 IP，这条规则基本无效。
    真正对撞库有用的是：应用层的账号维度锁定 + 强制验证码/mail code。
    本文件不解决这个问题，也不要以为配了它就算解决了。


================================================================================
🚨 上了 Cloudflare 之后必须同步改的两处 —— 不改会直接把站点打挂
================================================================================

这是全文件最重要的一段。Cloudflare 挡在中间会改变源站眼里的"客户端 IP"，
而本站有两个地方依赖这个 IP，不跟着改就会出事故：

【1】fail2ban 会把 Cloudflare 的边缘 IP 全部封掉 —— 站点直接全站 1020
    现在 docs/hardening-2026-09-24.md §2.2 里的过滤器读的是 Caddy 日志的
    "remote_ip"。挂了 Cloudflare 之后，remote_ip 变成 Cloudflare 边缘节点地址，
    于是 fail2ban 封的是 Cloudflare 自己。封完就是全站不可访问。

    修法分两步，缺一不可：

    ① 让 Caddy 相信 Cloudflare 送来的真实 IP。
       在 Caddyfile 的全局块里加（官方文档明确把这个用法列为 Cloudflare 场景）：

           {
               email ops@ai-memory.net
               servers {
                   trusted_proxies static private_ranges
                   trusted_proxies_strict
                   client_ip_headers CF-Connecting-IP X-Forwarded-For
               }
           }

       · trusted_proxies_strict 需要 Caddy v2.8+，本站是 v2.11.4，可以用。
         官方原话就是"上游代理（HAProxy、Cloudflare、AWS ALB、CloudFront 等）
         会把新连接地址追加到 X-Forwarded-For 右侧，建议启用 strict，
         因为最左边的 IP 可能被客户端伪造"。
       · 上面只信任了私有段（private_ranges）。**如果你的 Caddy 收不到来自
         Cloudflare 的连接，说明 Cloudflare 就在同机上或走内网，那没问题；
         若 Caddy 是直接暴露公网被 Cloudflare 回源，则必须把 Cloudflare 的
         回源段整个列进来**，段列表每天可能变，用这个命令取当前的：
             curl -s https://www.cloudflare.com/ips-v4 https://www.cloudflare.com/ips-v6
       · client_ip_headers 里把 CF-Connecting-IP 放第一位 —— 这个头是
         Cloudflare 自己写的、客户端改不了，比 X-Forwarded-For 可信。

    ② 改 fail2ban 过滤器，改读 client_ip 而不是 remote_ip。
       先确认字段真的出现了（trusted_proxies 生效后 Caddy 才会往访问日志里加）：

           tail -1 /var/log/caddy/access.log | python3 -m json.tool | grep -i '"ip'

       看到 client_ip 之后，把 /etc/fail2ban/filter.d/caddy-scanner.conf 的
       failregex 里 "remote_ip":"<HOST>" 换成 "client_ip":"<HOST>"，
       然后 systemctl restart fail2ban，再 fail2ban-client status caddy-scanner
       确认没在封 Cloudflare 的段。

    ③ 上线后的第一天，每天都看一眼：
           sudo fail2ban-client banned | grep -E '103\.|104\.|172\.(6[4-9]|7[01])|173\.245|188\.114|190\.93|197\.234|198\.41|162\.15[89]|141\.101'
       命中任何一条都说明 ① 或 ② 没做对，立刻停掉 fail2ban 的 caddy-scanner jail。

【2】看板与统计会失真
    stats/stats-gen.py 现在按 Caddy 日志里的客户端 IP 区分真人/爬虫、内外网。
    同样地，它会先看到一堆 Cloudflare 边缘 IP。① 做完之后日志里就是真实 IP 了，
    这一步顺带修好，但要重新跑一次 stats-gen.py 并核对卡片数字是否回到合理区间。

【3】Caddy 那套拦截不要因为"有 Cloudflare 了"就撤掉
   Cloudflare 只挡边缘。任何人都能拿着 35.227.140.175 直连源站绕过它。
   两层都留着才叫纵深防御。要真正藏住源站，得换 IP + 只放行 Cloudflare 回源段
   + 全面开橙云代理，那是另一件事，不在本文件范围内。

验收（挂上去当天逐条跑，在服务器上执行）
================================================================================
# 1. 站点活着
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/                       # 200

# 2. 扫描路径被挡（Cloudflare 的 Block 默认返回 403，也可能被你配成 404）
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/.env                   # 403/404
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/.DS_Store              # 403/404（大小写变体）
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/WP-ADMIN/              # 403/404
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/backup.sql             # 403/404

# 3. 门面文件一个都不能被拦 —— 这几条返回 403 就说明规则写错了，立刻回滚
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/robots.txt             # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/sitemap.xml            # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/llms.txt               # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/.well-known/security.txt  # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/legal.html             # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/favicon.ico            # 200
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/og-image.png           # 200

# 4. 关键接口不能被打挂（最容易误伤的两个）
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://ai-memory.net/api/auth/login # 400/401，不能是 403
curl -s -o /dev/null -w '%{http_code}\n' https://ai-memory.net/api/ops/backup-status  # 401，不能是 403

# 5. 方法白名单没有误伤 POST
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://ai-memory.net/api/leads      # 400/401，不能是 405

# 6. 源站直连仍然工作（Cloudflare 之外的那一层还活着）
curl -s -o /dev/null -w '%{http_code}\n' -k --resolve ai-memory.net:443:127.0.0.1 https://ai-memory.net/   # 200

# 7. 测试子域的国内线路实测（决定要不要动主域的判据）
#    在测试子域上挂一周，用国内机器跑：
curl -o /dev/null -s -w 'DNS %{time_namelookup}s  TLS %{time_appconnect}s  TTFB %{time_starttransfer}s  总计 %{time_total}s\n' https://test.ai-memory.net/

如果哪天升到 Business，规则 1 可以整条换成下面这一句，语义与 Caddy 那份一致：

http.request.uri.path matches r#"(?i)^/(\.git|\.env|\.data|\.ds_store|\.aws|\.ssh|\.svn|\.hg|\.vscode|\.idea|_preview|index\.html\.|wp-|xmlrpc\.php|phpinfo|phpmyadmin|pma|adminer|config\.php|docker-compose|Dockerfile|server\.py|requirements\.txt|backup|database|node_modules|vendor)|\.(py|json|orig|md|log|bak|save|tmp|sql|db|sh|env|ini|conf|prev|old|swp)$|/\.(git|env|aws|ssh|svn)(/|$)"#

为什么用 r#"..."# 原始字符串：Cloudflare 官方的建议就是正则一律用原始字符串语法，
引号字符串那套转义规则（尤其是反斜杠要双重转义）极易出错，官方原话是
"quoted string syntax has complex escaping rules and can lead to unexpected behaviors
if not thoroughly tested"。

另外 Cloudflare 的正则引擎是 Rust regex crate，**不支持反向引用与前后查找
（lookaround）**。上面这条正则没有用到这些特性，所以可以直接用；但你以后自己
往里面加东西时要留意这个限制。Caddy 用的 Go RE2 同样不支持 lookaround，
两边限制恰好一致，所以这条表达式在两侧可以共用。
